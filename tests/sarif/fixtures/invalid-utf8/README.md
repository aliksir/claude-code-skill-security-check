# invalid-utf8 fixture (issue #24)

A `SKILL.md` that tells apart the two things a scanner might take an
artifact digest over: the **raw bytes** of the file, or the **string**
obtained by decoding those bytes as UTF-8.

For well-formed UTF-8 the two give the same SHA-256, so an ordinary
fixture cannot show which one an implementation uses. This file is not
well-formed UTF-8, so the two values differ.

## What is in the file

`SKILL.md` is 577 bytes. Four of them are not ASCII, and they sit inside
an HTML comment in the body:

| Offset | Bytes | Meaning |
|---|---|---|
| 334 | `80` | a lone UTF-8 continuation byte |
| 335–337 | `ED A0 80` | the lone surrogate U+D800 in WTF-8 encoding |

Every other byte is ASCII, and line endings are LF.

The rest of the body is the sample skill text from the upstream drift
demo, including a `curl … | sh` line. It is test data. Nothing in this
repository executes it.

## The three values

| Input | SHA-256 over raw bytes | SHA-256 over the decoded string |
|---|---|---|
| this file | `0e5f6446b6c4e104a00a87655b759c4a5e5e6031b71f101a59e89156613d365b` | `eec1f1320f378b8a269c31429db72e015105571552ebf19e8db161da57808c1d` |
| this file with the lone `80` at offset 334 changed to `81` | starts with `1546f3f1` | `eec1f1320f378b8a269c31429db72e015105571552ebf19e8db161da57808c1d` (unchanged) |

"Decoded string" means: decode as UTF-8 with each invalid sequence
replaced by U+FFFD, then hash the UTF-8 encoding of the result.

The second row is why the basis matters. `80` and `81` both decode to
U+FFFD, so two different files share one digest under the string basis.
Under the raw-byte basis they do not.

## How this repository uses it

[`tests/sarif/artifact-digest.test.mjs`](../../artifact-digest.test.mjs)
runs the file through `enrichWithArtifactDigest` in
[`lib/sarif/artifact-digest.mjs`](../../../../lib/sarif/artifact-digest.mjs)
and asserts that the emitted `sha-256` equals the raw-byte value above,
and does not equal the decoded-string value. It also checks the three
values in the table and the byte layout, so a damaged checkout fails on
the layout check before any digest is compared.

## Do not edit this file as text

- Do not open and save `SKILL.md` in a text editor, and do not let a
  formatter or linter rewrite it. Saving it as text can replace the
  invalid bytes or change the line endings, and then the values above no
  longer match.
- [`.gitattributes`](../../../../.gitattributes) pins this path to
  `-text binary`, so Git does not convert its line endings or diff/merge
  it as text. If the file moves, update the path on that `.gitattributes`
  line to the new location.
- To replace the file, copy the bytes and re-run the checks below.
- When fetching it from GitHub over the REST API, use the *git blobs*
  endpoint. Observed on 2026-10-12 for the same blob in the upstream
  repository (skills-lock/skil-lock): the default JSON response of the
  REST *contents* endpoint reported `size` 577 and the blob's SHA, but
  its base64 `content` decoded to 583 bytes and differed from the blob.
  The *git blobs* endpoint returned the original 577 bytes.

## Checks

```sh
sha256sum tests/sarif/fixtures/invalid-utf8/SKILL.md
# 0e5f6446b6c4e104a00a87655b759c4a5e5e6031b71f101a59e89156613d365b

git hash-object tests/sarif/fixtures/invalid-utf8/SKILL.md
# d0a8f22336cd5c4589d23bec01271884f4a63613

git check-attr -a tests/sarif/fixtures/invalid-utf8/SKILL.md
# binary: set, diff: unset, merge: unset, text: unset

node --test tests/sarif/artifact-digest.test.mjs
```
